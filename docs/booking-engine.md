# Own booking engine: Beam checkout (Stripe the fallback), Cloudbeds as master

This is the runbook for the direct booking engine on magicsamui.com: how it works, how to switch it on, how to test it, and what to do when something goes wrong. **Beam** (beamcheckout.com) is the payment provider the owner chose for go-live (owner decisions of 21 Oct 2026); **Stripe** stays the one-variable fallback (`BOOKING_PAYMENT_PROVIDER=stripe` and a redeploy, section 6). Until the owner-gated code switch `LIVE_FULFILMENT_READY.beam` is flipped (design S7.1, not part of this build), beam-live is locked in code and production keeps taking real payments through Stripe exactly as before. The Beam companion notes (the Stage B owner checklist, the Beam API facts, the demo) are in `docs/booking-beam-preview.md`; the design is `beam-design-v2.json` (steps S2.0-S6.1).

**Short version**
- With **no new environment variables**, nothing changes. `/booking` shows the Cloudbeds engine as today, and `/booking-preview` stays a noindex demo (locally and on preview deployments; on the **production** deployment it shows "Payments locked" until `BOOKING_TOKEN_SECRET` is set, because the public demo secret is never accepted there).
- Cloudbeds stays the master for availability, prices, closures and OTA sync. Eldor keeps managing rooms and prices in Cloudbeds.
- The payment provider only moves money. Stripe is the owner's existing Thai Stripe account, the one already connected to Cloudbeds as its gateway (owner, 2026-10-06). Beam is the owner's Beam merchant account (Lighthouse), which must be held by Pakwan Samui LP (section 10).
- The guest pays 100% up front, plus an openly shown "Payment processing fee": 5% on Stripe; on Beam 3% by card or e-wallet and **no fee with Thai PromptPay QR** (owner decision 1). On Beam the guest chooses "Card or e-wallet" or "Thai PromptPay QR" on our payment step, and the Beam payment page offers only that group.
- **Beam, the owner decisions of 21 Oct 2026:** (1) PromptPay is fee-free, cards and e-wallets carry the 3% fee; (2) e-wallets (Alipay, LINE Pay, TrueMoney, ShopeePay; WeChat Pay once Beam approves it) are on at launch, with cards; (3) a payment that succeeds after its hold was released raises a CRITICAL alert and the owner re-books the guest if the unit is free, otherwise refunds in full in Beam Lighthouse (nothing is refunded automatically); (4) a 50% cancellation refund Beam can't make (PromptPay and the e-wallets) goes by manual bank transfer (section 8); (5) Stripe stays the instant fallback; (6) the Cloudbeds confirmation email is the guest's written confirmation (`CLOUDBEDS_SEND_STATUS_EMAIL=true`, a beam-live checkout condition): Beam sends no receipt.
- **The DIRECT code is honoured** (owner decision 1, 2026-10-06): on the own page it sells Cloudbeds' own "Direct booking rate" plan (not synced to the OTAs), with the base price struck through. Switch: `BOOKING_DIRECT_PROMO` (default on). A first DIRECT test booking went through on 2026-10-07, once the plan was opened to the own page's source (Stage B log; owner report, folio details pending), so Cloudbeds priced that hold at the Direct rate; the rest of Stage B case 24 (folio check, mixed cart) is still open. If it ever prices it at the base rate, every such booking is refused safely (nothing charged) with the alert "DIRECT bookings blocked: …" - then set `BOOKING_DIRECT_PROMO=off`.
- **Automatic discounts** (owner decision, 2026-10-07): with no code, the own page also sells Cloudbeds' public discount plans "Last minute 10% off" (and any plan named "Early bird..." the owner creates) whenever Cloudbeds offers them for the stay and they are cheaper than the base rate, with the base price struck through and the plan's name. Never "Non-refundable 10% discount" or any plan whose name reads as non-refundable (other refund terms; section 1, Guarantees, lists the spellings), packages (Breakfast) or promo-code plans. Switch: `BOOKING_AUTO_DISCOUNTS` (default on). Each such plan must be open to the own page's source in Cloudbeds (4.B step 7), else its bookings are refused (nothing charged, alert naming the fix). Whether Cloudbeds prices our hold at such a plan is **not proven yet**: Stage B case 27 (with an early bird plan), else the first real Last minute booking (Stage C step 8). If it prices it at the base rate, every such booking is refused safely (nothing charged) with the alert "Automatic discounts blocked: …" - then set `BOOKING_AUTO_DISCOUNTS=off`. "Long term booking" was one of them until the owner put "Long term" behind the code `LONGSTAY` (next point): it is no longer sold automatically, as a plan with a promo code never is.
- **Any Cloudbeds promo code works** (owner decision, 2026-10-07): the "Long term" plan (now 26% off, 7+ nights) sits behind a Cloudbeds promo code (e.g. `LONGSTAY`), so it is never shown automatically, and the own page accepts **any** code the owner sets up on a Cloudbeds rate plan, not only DIRECT, with no code change and no Vercel setting. A code is valid when Cloudbeds lists a plan carrying it for the stay (any case); that plan's rows are sold like the Direct rate (cheapest wins, stay rules, exact price check), labelled "<plan name> - code <CODE>" (e.g. "Long term - code LONGSTAY"). An unknown code is answered "Code X isn't valid for these dates." (never an error), and a plan whose name reads as non-refundable is never sold (a note points to `/booking/classic` or WhatsApp). DIRECT keeps its own mapping and wording, exactly as before. The same switch covers every code: `BOOKING_DIRECT_PROMO=off`. Owner setup: 4.B step 8; not proven live yet: Stage B case 28 (LONGSTAY, 7 nights). If Cloudbeds prices such a hold at the base rate, it is refused safely with the alert "Code <CODE> bookings blocked: …".

## 1. Architecture

### Providers and modes

`BOOKING_PAYMENT_PROVIDER` chooses the provider. The provider and its keys then give the payment mode.

| Mode | When | Money | Cloudbeds reservation |
|---|---|---|---|
| `demo` | Default (no env), or `BOOKING_PAYMENT_PROVIDER=demo` | Simulated | None |
| `beam-playground` | `provider=beam` (or, with no provider variable, the legacy rule: `BEAM_API_BASE` set), `BEAM_API_BASE=https://playground.api.beamcheckout.com`, `BEAM_MERCHANT_ID` and `BEAM_API_KEY` | Beam Playground test money (test cards, simulated wallets) | **Real** with `CLOUDBEDS_API_KEY_BOOKING` (guarded like stripe-test, needs Redis; Stage B). | `beam-live` | `provider=beam`, `BEAM_API_BASE=https://api.beamcheckout.com`, and **every** Beam live condition below - one of them is the code switch `LIVE_FULFILMENT_READY.beam`, which is `false`: **always locked in code** until design S7.1 | Real cards, e-wallets and PromptPay | Real |

**Live conditions.** All of these must hold, or the config throws `live_payments_locked`. Then nothing is charged, the page shows a locked message with the WhatsApp link, and the server log lists what is missing.
- `BOOKING_PAYMENT_PROVIDER=stripe`
- A live key
- `BOOKING_ALLOW_LIVE_PAYMENTS=true`
- `VERCEL_ENV=production`
- `CLOUDBEDS_API_KEY_BOOKING` and a numeric `CLOUDBEDS_PROPERTY_ID`
- `STRIPE_WEBHOOK_SECRET` (`whsec_…`)
- `BOOKING_SWEEP_SECRET` (or Vercel's `CRON_SECRET`), 16+ characters: the sweeper is the only recovery for lost holds once Stripe stops retrying
- Upstash Redis
- A strong `BOOKING_TOKEN_SECRET`
- Live Cloudbeds data, with `BOOKING_DATA_SOURCE` not set to `demo`
- `BOOKING_STRIPE_MOCK` not set to `true`
- `LIVE_FULFILMENT_READY.stripe` (true in code)

The full matrix is tested in `src/lib/booking/stripeConfig.test.ts`.

**Beam live conditions** (`beamLiveBlockers` in `config.ts`, design S3.4; tested in `beamConfig.test.ts`). With `BEAM_API_BASE` on the live base, all of these must hold, or the config throws `live_payments_locked` (nothing charged, the locked page with WhatsApp):
- `BOOKING_PAYMENT_PROVIDER=beam`, `BEAM_API_BASE=https://api.beamcheckout.com`, `BEAM_MERCHANT_ID`, `BEAM_API_KEY`
- `BEAM_WEBHOOK_HMAC_KEY`: base64, at least 16 bytes once decoded
- `BOOKING_ALLOW_LIVE_PAYMENTS=true` *(checkout only)*
- `VERCEL_ENV=production`
- `CLOUDBEDS_API_KEY_BOOKING` and a numeric `CLOUDBEDS_PROPERTY_ID`
- Upstash Redis, a strong `BOOKING_TOKEN_SECRET`, live Cloudbeds data (`BOOKING_DATA_SOURCE` not `demo`)
- `CLOUDBEDS_SEND_STATUS_EMAIL=true` *(checkout only)*: the Cloudbeds confirmation email is the guest's written confirmation (owner decision 6)
- `BOOKING_SWEEP_SECRET` (or `CRON_SECRET`), 16+ characters
- `LIVE_FULFILMENT_READY.beam` (code): **false** in this build, so while it is false the error names only the code switch and the rest of the list follows in its message ("Also missing: ...")

The two *checkout only* conditions are skipped for **finishing** payments (`getFulfilmentConfig`, the Beam drain): an emergency stop or a switched-off Cloudbeds email stops new Beam checkouts but never the confirmation or release of Beam payments already started. `CLOUDBEDS_BEAM_PAYMENT_METHOD` is deliberately not a live condition (as Stripe's method is not): a missing or refused value stops checkout with the "payment method is not set up" alert, while paid bookings, releases and the sweeper keep working. `BOOKING_PAYMENT_PROVIDER=beam` without Beam keys stays the demo locally, but is a config error (`payment_misconfigured`: checkout refused, the page locked) on the production deployment or next to `CLOUDBEDS_API_KEY_BOOKING`; an unrecognised `BEAM_API_BASE` is `invalid_beam_base`.

**Both providers are hold-first.** The Beam modes (design S3.1) have exactly the Cloudbeds side of the Stripe modes: the Cloudbeds hold before any payment page, the guest's details (and postcode) sent at checkout, 100% up front, the Standard rate only with no add-ons or site-side breakfast plan, the base rate, DIRECT and every other Cloudbeds promo code, the automatic discounts, the stay rules under the unit lock, the folio read-back before the payment page, the test-mode guard, the brakes, the sweeper and the alerts. Wherever this runbook says "Stripe modes" about the Cloudbeds side (sections 1, 3 and 7), the Beam modes behave the same way. What differs on Beam: the payment page (a Beam payment link for the guest's method group), the fee per method, the webhook, the sweeper's payment check, the texts written to Cloudbeds and the refunds (below, "Booking flow with Beam" and "Guarantees with Beam").

**Beam hold identifiers.** A Beam hold's `thirdPartyIdentifier` is `{ref}-B` in beam-live and `{ref}-B-TEST` in beam-playground (Stripe keeps `{ref}` and `{ref}-TEST`). Stripe code, and the pre-Beam production code after a rollback, never parses a `-B` id; Beam runs parse only `-B` ids (`parseBeamHoldIdentifier` in `lock.ts`), so each sweeper run owns the orphan holds of its own provider. In Cloudbeds the id is shown as the reservation's "Source Reservation ID".

- **The webhook** (`src/app/api/beam/webhook/route.ts`, `lib/booking/beamWebhook.ts`; runtime nodejs, `maxDuration` 30, every Beam call of a delivery bounded by 25 s): finishes Beam payments through the active Beam config or, after a switch away from Beam, the Beam drain. It answers 503 **before the body is read** when there are no Beam deps (log `beam_webhook_unconfigured`, no data) or no `BEAM_WEBHOOK_HMAC_KEY` (`beam_webhook_unconfigured {hmacKey: false}`); 413 over 64 KB; 401 for a missing or bad signature; 200 for a signed body that is not JSON or names nothing of ours; 503 when Beam or Redis can't be read or the paid marker can't be written (Beam retries every non-2xx answer, up to 10 times); 200 once the paid marker exists, whatever fulfil does next (the sweeper and the return page retry it). The body is only ever used to name the resource: the event comes from the body's ids (the unsigned `X-Beam-Event` header is a hint, a disagreement is logged), and every payment is re-read from Beam.
- **The return page** polls `/api/booking/status` (2 s, then each wait x1.5 up to 15 s, for 15 minutes); each status request reads the link and its charges (2 Beam calls; for a closed link whose hold is already released, no second reading to release it again), and a finished booking (its done marker, this booking's ref and amount) is answered with no Beam call at all.
- **Cancel / Back**: Beam's Cancel button lands on our page with `?resume=payment&reason=cancelled&ref&t`, which calls abandon at once (disable the link, release the hold); a later Pay in the tab abandons the earlier attempt first. A payment that is paid is fulfilled, never cancelled; one still being confirmed by the bank answers `pending` (the return page, never a second payment).
- **Ownership**: a Beam payment is ours by its Redis PaymentRecord or, when that is gone, by its HMAC-signed note (signed with `BOOKING_TOKEN_SECRET`; booking facts and yes/no flags only, no personal data). A link with neither is not ours (e.g. the owner's own Lighthouse links). A link that disagrees with our record (another booking ref, another Beam merchant, the amount or currency) is never "not ours": fulfil hands it to the owner (CRITICAL "needs attention").

### Guarantees

- **Hold before charge.** We never charge for a room we don't hold. Inventory is only ever decremented in Cloudbeds, the system that feeds the OTAs.
- **Our own checkouts never race each other.** The fresh restriction + availability check and `postReservation` run under a Redis lock per **physical unit** (HM, SR, GS, SVL, TUX, TUXL; a combination type locks all its units). The hold record - with its units and dates - is written **before** the lock is released, and every checkout refuses a cart that overlaps one of our open holds. So our own serialisation does not depend on how fast Cloudbeds' `getAvailableRoomTypes` reflects a new reservation, including combination types built from shared units (tested with a fake whose availability lags and would overbook). This covers **open** holds only: once a booking is confirmed it leaves the open-holds index, and from then on Cloudbeds' Split Inventory links are the only guard, against our own later sales too (section 9). Only the race against an OTA booking remains, as with the Cloudbeds engine - and Stage B tests 10, 11 and 14 check that Cloudbeds refuses it, in both directions of each link, and that pending holds block inventory.
- **No lost holds.** A hold *intent* is written to Redis **before** `postReservation`. If the answer never arrives (timeout, 5xx, a success without an id, the function killed mid-call), the intent stays open, the owner gets an alert, and the sweeper finds the reservation by its `thirdPartyIdentifier` and releases it once it is 40+ minutes old - whether Cloudbeds created it as `not_confirmed` or `confirmed`. A matched orphan becomes a hold record carrying the **intent's** time, so a release that fails is retried by every later run on that age (and alerted at once). An intent never matched is dropped after 12 hours **with an alert** naming the third-party id to check by hand. A success with a valid id but no readable total is cancelled at once.
- **The sweeper checks ages itself.** It only releases a hold it can prove is older than 40 minutes: our own record's time, the intent's time, or - only for a reservation we have no record or intent of - Cloudbeds' creation time read cautiously (the v1.3 `getReservations` has only `dateCreated`, with no zone - property-local by Cloudbeds' convention, not proven - read as UTC: never older than it is when it is Bangkok or UTC time, up to 7 hours younger). It never relies on how Cloudbeds interprets the `resultsFrom`/`resultsTo` window.
- **The sweeper fails loudly.** A run whose Cloudbeds listing fails is not recorded as a sweep (so checkout's "sweeper has not run" alert fires), answers HTTP 502 (the cron's `curl -f` fails), counts unresolved intents in `openHolds`, and alerts after 3 such runs in a row.
- **The 30 s function limit.** The checkout route answers within 25 s: it refuses to start a hold with less than 17 s left, reads the hold's folio back only with 8+ s left (otherwise it cancels the hold and answers 503 "systems are slow", nothing charged), skips the best-effort pending mark and note when short of time, sizes the Stripe call (timeout, retries) to what is left, and gives the hold back with a 503 if the Stripe call can't fit. Every Cloudbeds write on the checkout path is bound to the same deadline (`CloudbedsWriter.bounded`): the wait for a rate-limit token, the request timeout and any 429 retry are cut to the time left, and a call with under 1.5 s left is not sent at all. So `postReservation` can never still be running when the platform stops the function; if its answer is cut short, the "outcome unknown" alert is sent and the sweeper releases the hold by its intent.
- **Test and live never touch each other's holds.** Outside live the `thirdPartyIdentifier` is `MSV-…-TEST`; each sweeper only touches its own mode's holds and records. Stage B and live may share one Redis: hold and intent records carry their mode, and every key that is not tied to one record - alert repeat claims, stored critical alerts, the last successful sweep, the failure counters and the paid-but-unconfirmed list - is kept per mode (`msv:live:…` vs `msv:stripe-test:…`), so a test deployment can never hide a dead live sweeper or re-send, clear or suppress a live alert.
- **A paid booking is never left behind.** As soon as fulfil sees a session paid it sets the paid marker, lists the session as paid-but-unconfirmed and adds a reservation note in Cloudbeds: "PAID via Stripe pi_… - do NOT cancel". The hold stays in the sweeper's index until fulfil's done marker exists, and the sweeper retries every paid-but-unconfirmed session on every run (beyond the 48 h Stripe lookback and Stripe's 3 days of webhook retries) until its paid record expires after 30 days (section 9). The failure alert names the booking (ref, Cloudbeds reservation, amount); after 2 hours unconfirmed it becomes the CRITICAL "URGENT: paid booking … still not confirmed" (stored and re-sent until delivered). A payment Cloudbeds refuses outright (`success:false` or an HTTP 4xx other than 429 on `postPayment`, or no usable payment method configured; a lasting 429 stays the retrying warning) is CRITICAL at once: "URGENT: paid booking … Cloudbeds refused to record the payment".
- **Fulfil never undoes staff work.** It confirms only a reservation that is still "Confirmation pending"; one staff already confirmed, checked in or checked out is left as it is, and any other status goes to the owner (`needs_attention`).
- **Only the base rate is sold (and the Direct rate for DIRECT, another code's plan for that code, and the automatic discount plans).** In Stripe and Beam modes availability uses Cloudbeds' base (BAR) row only (the exceptions are the next three points): the row with no `derivedType` whose `ratePlanNamePublic` is `"default"`, empty or absent (any case; live `getAvailableRoomTypes` sends `"default"`). A room type that comes back with only a derived or other named plan (Breakfast package, long stay, non-refundable) is shown as unavailable (log `cloudbeds_no_base_rate`; when that leaves every room unavailable in a search, also the error line `cloudbeds_no_base_rate_all` and the owner alert "Online bookings stopped: Cloudbeds returned no base rate for any room") instead of being sold as that plan under the "Standard Rate - Room only" label. As a second check, checkout refuses a hold (409 `unavailable`, which the page shows as "no longer available for your dates"; alert) when `getRatePlans` lists the rate being sold as derived - the exceptions are the promo code's rate (the Direct rate, or another code's plan) and the automatic discount selected for the booking (below).
- **DIRECT sells Cloudbeds' own Direct rate** (owner decision 1; `BOOKING_DIRECT_PROMO` on, Stripe or Beam with live Cloudbeds rates). The browser sends only the code, never a rate. With a valid code (`BOOKING_PROMO_CODE`, default `DIRECT`, any case; leave it unset, section 2) the server asks `getAvailableRoomTypes` with `promoCode` = `CLOUDBEDS_PROMO_CODE` (default `Direct`) and reads `getRatePlans` (not filtered by room type) to learn which `rateID`s carry that promo code, per room type: `getAvailableRoomTypes` rows carry no promo code or plan id, and each room type has its own Direct rate id (Honeymoon: 3195765), so nothing is hard-coded and nothing is matched by name. A room's Direct row is sold instead of its base row when it is sellable (a unit left, a rate on every night), cheaper than the base row, and derived from it (`parentRateID`, when sent, is the base row's rate id); otherwise the base row is sold as without a code and the room card says the code doesn't apply to it (a code that applies to no available room shows "doesn't apply to these dates"). Prices show the base price struck through and "Direct rate - code DIRECT"; the 5% fee is on the Direct total. The search page's perk and the code box hint say "Use code DIRECT for our best direct rate.", never "every room": the Direct plan is confirmed on the Honeymoon Suite only (section 3). Checkout re-quotes from Cloudbeds with the code exactly as without it (one fresh read of the shared rate-plan index); the availability re-check under the lock reads without the code and without automatic discounts (base rows only, no index read), because the stay-rule read under the same lock re-confirms the discounted row on fresh data. Under the unit lock the stay rules are checked on the Direct row **and** its base row over all stay nights (the highest positive minLos and lowest positive maxLos of either, closed to arrival / departure, blocked or no room on either; 0 = no limit), and the derived-rate defence allows exactly that rate - confirmed by `getRatePlans` as carrying the promo code and derived from the base row it was priced next to - and still refuses any other derived row. The hold sends `rooms[0][roomRateID]` = the Direct rate id plus `promoCode` (v1.3: "'rateID' parameter required for using 'promoCode'"). The price check is unchanged (hold and folio must equal the quoted Direct rooms subtotal); a hold priced at exactly the base-rate total is classified apart: cancelled, nothing charged, one alert "DIRECT bookings blocked: Cloudbeds priced the Direct rate at the base rate - set BOOKING_DIRECT_PROMO=off and redeploy", and the guest is offered `/booking/classic` (where Cloudbeds applies the code) or WhatsApp. With `BOOKING_DIRECT_PROMO=off`, or without live Cloudbeds rates (MOCK), a guest who enters the code (or any other code, next point) gets a note linking the classic booking page instead of the code being silently ignored. The demo keeps its site-side % (`BOOKING_DEMO_PROMO_PCT`).
- **Any other Cloudbeds promo code sells its own plan** (owner decision, 2026-10-07: "Long term", 26% off, 7+ nights, behind a code such as `LONGSTAY`, never shown automatically; and any code the owner sets up later, with no code change). Same switch and same deployments as DIRECT (`BOOKING_DIRECT_PROMO` on, Stripe or Beam with live Cloudbeds rates); DIRECT itself keeps its mapping (`BOOKING_PROMO_CODE` → `CLOUDBEDS_PROMO_CODE`), its "Direct rate - code DIRECT" label, its copy and its call pattern unchanged. A typed code (trimmed, any case, 1-32 letters, digits, `-`, `_`; `?promo=` and the homepage search bar carry it too) other than DIRECT is looked up in the rate-plan index first: the search reads `getRatePlans` (all room types, the same read the automatic discounts use, 60 s cache) **before** availability, and the code is valid when at least one plan carries it as its `promoCode` (compared trimmed and case-insensitively) - any plan, whatever its name, except one whose public name reads as non-refundable (the same spellings as for automatic discounts, below): such a plan is never sold here (the page has no refund terms for it), and a code carried only by such plans gets a calm note "Code X is for a non-refundable rate, which can't be booked on this page - our classic booking page applies it, or message us on WhatsApp …" with the classic-page link. A code no plan carries for the stay gets "Code X isn't valid for these dates." with no promo-code read and the prices as without a code (never an error page). A valid code is asked of `getAvailableRoomTypes` with **Cloudbeds' own spelling** of it (e.g. the plan's `LongStay` for a guest's `longstay`), plain and with the code as for DIRECT, and the plan's rows (by rate id, per room type) are sold exactly like the Direct row: derived from the base row it is sold next to (`parentRateID`, when sent), cheaper, sellable on every night; per room the cheapest of base / automatic / code row wins (a tie goes to the code); a room without the plan, or where it loses, says the code doesn't apply to it, and a code no available room gets says "doesn't apply to these dates". Labels: the search line "Code LONGSTAY applied: Long term", each room "<its plan's public name> - code LONGSTAY" (at most 80 characters: a long plan name is cut, never the code) on the card, the summary, the payment step and the paid return page; the Stripe line "Standard Rate (Long term)"; the hold's note "Long term (code LONGSTAY)."; GA4 `coupon` = the code. Checkout re-quotes with its own fresh index read (the gate reads of a multi-guest cart reuse it), resolves the code again, checks the stay rules of the plan's row **and** its base row under the lock (Long term's minLos 7: a 3-night stay is refused with "needs a minimum stay of 7 nights" before any hold, should Cloudbeds ever offer it), lets the derived-rate defence allow exactly the row selected (it must still carry that promo code, not read as non-refundable, and be derived from the base row it was priced next to), holds `rooms[i][roomRateID]` = the plan's rate id with `promoCode` = Cloudbeds' spelling, and runs the same exact price check and folio read-back. A hold priced at exactly the base rate is classified apart: cancelled, nothing charged, the guest offered `/booking/classic` or WhatsApp ("We couldn't reserve your room at our "Long term" rate online just now …"), and one alert per code "Code LONGSTAY bookings blocked: Cloudbeds priced the "Long term" rate at the base rate - set BOOKING_DIRECT_PROMO=off and redeploy" (log `hold_code_at_base`; DIRECT keeps its own "DIRECT bookings blocked" alert). A plan not open to the own page's source is named in the "Cloudbeds refused the reservation" alert with where to tick it (next point).
- **Automatic discounts: Cloudbeds' public discount plans, no code** (owner decision, 2026-10-07; `BOOKING_AUTO_DISCOUNTS` on by default, Stripe or Beam with live Cloudbeds rates only - the demo is unchanged). Which plans: `BOOKING_AUTO_DISCOUNT_PLANS` (default `Last minute,Long term,Early bird`), case-insensitive **prefixes** of the plan's public name (`ratePlanNamePublic`), so "Last minute 10% off", "Long term booking" and any "Early bird..." plan the owner creates qualify. A plan is never sold automatically, whatever the list says, when it is not derived (`isDerived`), carries a promo code (it needs the code; the Direct rate keeps its own path), reads as non-refundable anywhere in its whole public name (other refund terms than the page's policy; the page shows at most 60 characters of the name, the check reads all of it): "non-refundable" with any separator, an ASCII or Unicode hyphen or dash, or none ("nonrefundable"), "Non-Ref" / "NonRef", "NRF", "no refund(s)", "not refundable", "unrefundable", and "prepaid" / "pre-paid" / "advance purchase" (in hotel naming usually a non-refundable rate; a false match only sells the base rate), or is not cheaper than its base row on the stay. The name check is a backstop only: it can't see a plan's cancellation policy, so every automatic plan must carry the page's refund terms (4.B step 7); packages (Breakfast) and "bookings max 7 day stay" (same price) are not on the list. How: the search reads `getRatePlans` ONCE (all room types, the same read the Direct rate uses, at the same time as availability, 60 s cache shared by searches with and without the code; checkout reads it fresh) and learns which `rateID`s are automatic discount plans, per room type (`cloudbedsRateIndex`). That read never takes a plain search down: when it fails, or the call budget has no token left for it (availability takes its token first), the search shows the base rates (log `cloudbeds_rate_index_failed`) and a cached answer is served as it is - also when the index has changed since that answer was cached and availability can't be read again (e.g. the index read took the last budget token; log `cloudbeds_search_revalidate_failed`); checkout re-quotes anyway. A read that was sent and failed (HTTP error or 429, `success:false`, timeout) is not sent again for that stay for 20 s (`RATE_PLAN_FAIL_TTL_MS`): searches in that time, cached ones included, show the base rates at once with no Cloudbeds call and no budget token (the log line then ends "(remembered: not re-sent for 20 s)"); a search with the code and checkout still ask. A search with the code, and checkout, still refuse without it (the Direct rate and the price need it). `getAvailableRoomTypes` without a code already returns the public plans Cloudbeds offers for the stay (Last minute only inside its window; an early bird plan only inside its advance window), so the engine never second-guesses those windows. Per room type the **cheapest** of the base row, the Direct row (with the code) and the automatic discount rows is sold - a discounted row must be sellable on every night, cheaper than the base row and derived from it (`parentRateID`, when sent, is the base row's id); between discounted rows of the same price the Direct rate wins, else the first in Cloudbeds' answer (a row only as cheap as the base row is never sold: the base row is). Example (Honeymoon, 2027-11-08 rates, base 13,500 a night): an "Early bird 15% off" plan would sell at 11,475 with no code; with code DIRECT the Direct rate (10,800) beats it. (Until 2026-10-07 "Long term booking", 6% off for 7+ nights, was sold this way; "Long term" is now behind the code `LONGSTAY`, a code plan: next point.) The page shows the base price struck through and the plan's name ("Last minute 10% off", "Early bird 15% off"; the Direct rate keeps "Direct rate - code DIRECT"); a room whose code rate is beaten by an automatic discount says "Code DIRECT doesn't lower this room's price ... our "Early bird 30% off" rate is shown". Checkout re-quotes and picks the row itself (the browser never sends a rate). Cloudbeds must have the plan open to the own page's source (4.B step 7), else `postReservation` refuses the hold (see the next point). Under the unit lock the stay rules are checked on the plan's row **and** its base row (strictest wins, 0 = no limit), and the derived-rate defence allows exactly the plan selected (re-confirmed on fresh `getRatePlans`: derived, no promo code, an eligible name, derived from the base row it was priced next to). The hold sends `rooms[i][roomRateID]` = the plan's rate id, **no** `promoCode` (a cart that also has a Direct room sends the one reservation-level `promoCode` as before). The price check is unchanged; a hold whose automatic-discount rooms were priced at exactly their base rate is classified apart: cancelled, nothing charged, one alert "Automatic discounts blocked: Cloudbeds priced <plan> at the base rate - set BOOKING_AUTO_DISCOUNTS=off and redeploy", the guest offered `/booking/classic` or WhatsApp (a mixed cart whose Direct rooms were priced at base too also raises the DIRECT alert). The hold's note says "Automatic discount: <plan>.", the Stripe line "Standard Rate (<plan>)", and the paid return page shows the plan's name with the base price struck through; GA4 items carry the plan's name as `item_variant`.
- **A derived rate refused for the reservation source names the fix.** `postReservation` refuses a derived rate whose plan is not open to the hold's source with "Rate N is not available for this reservation. Verify the rate is bookable for these dates and for the reservation source." (live for the Direct rate on 2026-10-07, fixed by ticking the source in the plan: 4.B step 7). When the cart holds a discounted rate (a promo code's - Direct or any other code - or automatic), the "Booking stopped: Cloudbeds refused the reservation" alert adds the plan(s) (the one whose rate id the message names; every discounted plan in the cart when the message names no cart room's rate) and: "In Cloudbeds: Rates and Availability > Rate Plans & Packages > <plan> > 'Which sources is rate plan available for?' > tick the own booking page's source (CLOUDBEDS_SOURCE_ID), save." plus the switch that sells the base rate meanwhile (for a code other than DIRECT the alert adds that `BOOKING_DIRECT_PROMO=off` switches off every code, DIRECT included). When the rate id named is the **base** rate of a room in the cart, the alert names that room's base rate instead (no discount plan blamed, no discount switch: check that base rate in Cloudbeds). When the hold also carried the reservation-level `promoCode` (a room on the Direct rate in the cart) and the refused rate is not the Direct rate, the alert adds that the code may be the cause (Stage B case 24(d)): if bookings without the code go through, set `BOOKING_DIRECT_PROMO=off`.
- **No Cloudbeds fee on top of ours.** Cloudbeds applies taxes and fees per reservation **source**. The hold is sent with `sourceID` = `CLOUDBEDS_SOURCE_ID` (a fee-free source, 4.B step 3) when set, and its folio is always read back before the payment page: any Cloudbeds tax/fee or additional item on it, or any total that differs from the quoted rooms, cancels the hold before anything is charged. Our own fee line (5% Stripe) is the only fee on the folio. Fulfilment checks again (last resort, never cancels): Cloudbeds taxes/fees on a paid folio or a reservation filed under another source raise an alert.
- **A payment method must be set before anything is held.** With real Cloudbeds writes, checkout refuses (503 "message us", alert) while `CLOUDBEDS_STRIPE_PAYMENT_METHOD` (outside live: `CLOUDBEDS_STRIPE_TEST_PAYMENT_METHOD` when set) is unset, not a usable value or a Cloudbeds built-in method (section 2). On Beam the same holds for `CLOUDBEDS_BEAM_PAYMENT_METHOD` (outside live: `CLOUDBEDS_BEAM_TEST_PAYMENT_METHOD` when set), which must also not equal a set Stripe method variable; Stage B case 1 run **without** the Beam test variable proves that `postPayment` accepts the Beam(website) value, as for Stripe. The value is not compared with Cloudbeds' own list at runtime: the WI-0 script (section 6) checks it, and Stage B case 1 **run with `CLOUDBEDS_STRIPE_TEST_PAYMENT_METHOD` unset** proves `postPayment` accepts `Stripe(website)` (a payment recorded under the test method proves only the test method's value; if case 1 never ran without it, Stage C step 4 is the first proof). It is deliberately not a live-lock condition, so paid bookings, releases and the sweeper keep working while it is fixed.
- **Staff stay in charge.** A hold we had marked "Confirmation pending" that staff later confirmed by hand (no payment recorded) is never cancelled automatically: the owner is alerted instead. Checked-in / checked-out / no-show reservations are never cancelled. A **confirmed** reservation carrying an `MSV-` id that we have no record or intent of (e.g. staff re-booked a paid guest under the ref, or Redis lost the record) is never cancelled either: the owner is told once.
- **Never cancel a paid booking.** Release is refused when:
  - Stripe says the session is paid, open or processing;
  - our "paid" marker exists (set before any payment write);
  - the Cloudbeds folio already shows a payment.
- **Fulfil is idempotent.** It uses:
  - a Redis `SET NX EX 120` lock per session, so 5 concurrent calls produce exactly one `postPayment` (tested);
  - per-step markers (fee, payment);
  - a check of the folio's paid amount before `postPayment` (`balanceDetailed` read as an object **or** an array, as v1.3 allows; an unreadable paid figure is "unknown", never 0); a folio that already shows **part** of the amount (recorded by hand) goes to the owner (`needs_attention`) and the full amount is never posted on top;
  - a payment-**attempt** claim written before `postPayment` is sent: if its answer is lost (timeout/5xx), retries do not post again for 10 minutes while the folio catches up; after that, a folio still showing no payment gets one more post, and a folio whose paid amount can't be read goes to the owner (`needs_attention`) instead of a guess (tested with a fake that commits the payment after the retry read the folio);
  - a 30-day done marker.
- **The fee line never blocks a confirmation.** `postCustomItem` is tried first (so the folio balances), but if it fails the payment is still recorded and the reservation confirmed; the fee is retried once after confirming and, if that still does not succeed, the owner gets "the processing fee line is missing". When a payment problem hands the booking to the owner instead ("needs attention": part of the payment already on the folio, or a payment record in doubt), the fee is retried once before that and, if it still does not succeed, that alert says so too. A failed `postCustomItem` may still have added the item (a timeout or 5xx, in this run or an earlier one), so both alerts say: open the folio, add the "Payment processing fee" item once **only if it is not listed**, never twice. A paid folio that already carries additional items when fulfil reaches the fee line (someone added one by hand while the booking was being retried) gets **no** fee line from us: "the processing fee line was not added" asks the owner to check that exactly one is listed. So the alerts that ask the owner to settle a paid booking by hand say not to add the fee line by hand while it is still being retried.
- **Test money is labelled.** Outside live, the payment description and the reservation notes in Cloudbeds start with `TEST MODE - NOT REAL MONEY`. Set `CLOUDBEDS_STRIPE_TEST_PAYMENT_METHOD` to the exact `method` value of a separate Cloudbeds payment method (4.B step 5; never a value with spaces, which is refused) to keep test money out of the real "Stripe (website)" method's reports.
- **The fee line has one Cloudbeds item per mode.** Cloudbeds keeps the name and description sent the first time an `appItemID` is used and ignores them on later calls. So live uses `msv-payment-processing-fee` ("Payment processing fee") and every other mode `msv-payment-processing-fee-test` ("TEST - Payment processing fee"), and the item's note is static - no ref, no PaymentIntent. The per-booking ids are in the payment's description and in the "PAID via Stripe" reservation note. Test and live fees are therefore separate items in Cloudbeds' reports, and a Stage B test line can never label a live one.
- **Money units.** Satang (integers) everywhere in our code and in Stripe (THB is a 2-decimal currency). Conversion to baht happens **only** at the Cloudbeds boundary (`satangToBahtString`, `cloudbedsMoneyToSatang`).
- **No personal data** in URLs, tokens, logs, Stripe metadata or analytics. The guest's details go only to Cloudbeds (the reservation) and Stripe (`customer_email`, and `payment_intent_data.receipt_email` so Stripe sends the live receipt whatever the account's email settings are). Cloudbeds error messages are redacted before logging. The paid return page - where `purchase` fires - never prints the guest's email address ("to the email address you entered"), so no Google tag can pick it up from the page. **On Beam** the guest's details go to Cloudbeds only: Beam gets the booking reference, what was booked (room names, dates, nights, number of guests), the amounts and our signed note (booking facts and yes/no flags), never a name, email address or phone number (`collectPhoneNumber` false); the guest types any card or wallet details on Beam's own page, and the last four card digits Beam sends back are dropped when a charge is read (`parseBeamCharge`), so they are never logged or stored. Beam logs and alerts carry link, charge and refund ids, method names, amounts and booking refs only.
- **Analytics.** `purchase` fires once, only in a live mode (`stripe-live`, or `beam-live` once it is unlocked) on the production deployment, after the server reports paid **and** Cloudbeds confirmed (on Beam also for a booking answered from its done marker). `transaction_id` is the Cloudbeds reservationID and `value` is in baht. The status API returns `purchase` only then. On `/booking-preview*` gtag.js is loaded **only while the deployment takes real payments** (stripe-live or beam-live on production: Stage C and the soft launch run there, so their real purchases reach GA4 and the Google Ads import), and on `/booking-preview/return` also while live Stripe or Beam payments are only being **finished** (emergency stop, provider drain: `finishesLivePayments`), so the purchases of bookings already paid are still recorded. In demo, MOCK, test mode, the Beam playground and Stage B it never loads, so not even the layout's queued `page_view` is sent. Clarity never records `/booking-preview*` (privacy). `purchase` also needs `NEXT_PUBLIC_VERCEL_ENV=production` in the browser bundle (see section 2). The address-bar cleanup on `/booking` keeps the ad-click ids Google, Microsoft and Meta use for attribution (`gclid`, `gbraid`, `wbraid`, `gad_source`, `gad_campaignid`, `dclid`, `_gl`, `msclkid`, `fbclid`, `utm_*`) and drops everything else.
- **The fee is shown with the first price.** On Stripe every room card and the results header say "+ 5% payment processing fee" (every online payment pays it: cards, wallets and PromptPay), and the summary and payment step show it as its own line. On Beam (design S5.2, round 7) each room card says "+ 3% fee by card or e-wallet" and, on a line of its own, "No fee with PromptPay"; the results header says "Prices are for the stay; a 3% payment processing fee is added when you pay by card or e-wallet (none with PromptPay)."; until the guest chooses how to pay, the summary shows the card/e-wallet total with "No fee with Thai PromptPay QR", so a total never rises after the choice; the "Payment processing fee (3%)" line is shown for card or e-wallet and disappears with PromptPay (a 0 fee). The cancellation policy the guest agrees to says the fee is refunded only when the whole stay is refunded.
- **A hold never dies silently.** Every cancel by the checkout writes its reason into the Cloudbeds reservation note ("Hold cancelled by the booking page before any payment: ..."), and the sweeper writes what the payment page did when it releases a stale hold (never created / created but never attempted / started but not completed / attempt failed). An unexpected error after the hold (a bug, a dependency throwing) now expires the Stripe session if one exists, cancels the hold, notes it and alerts the owner ("Booking stopped: unexpected error after the hold") instead of leaving the hold for the sweeper (2026-10-20).
- **Alerts are not lost.** A failed send is logged and frees the repeat-suppression key, so the next occurrence retries; alerts are sent after the response with an 8 s relay/SMTP limit; **critical** alerts are stored in Redis until delivered and re-sent by every sweeper run (section 7).
- **Always the THB price shown.** Checkout Sessions pin Adaptive Pricing off, so no guest is charged a converted local-currency amount with Stripe's FX margin, and refunds stay in THB. Stays above Stripe's maximum charge (THB 999,999.99) are refused **before** any Cloudbeds write ("message us on WhatsApp").

### Guarantees with Beam (design S2.3-S4.10)

Every guarantee above holds for Beam bookings too (the hold first, the unit locks, the intents, the folio check, the paid marker, staff in charge, never cancelling a paid booking, idempotent fulfil, the fee line never blocking a confirmation, labelled test money, satang, no personal data, alerts never lost). On top of them:
- **One payment link per hold, for the guest's method group.** "Card or e-wallet" links offer cards plus the e-wallets (while `BEAM_EWALLETS` is on) at the card fee; "Thai PromptPay QR" links offer only the QR, with no fee and no fee line. A quote whose fee is not the group's, or a group the checkout does not take, never reaches Beam. The amount is fixed in THB satang (`order.netAmount`), so the guest pays exactly the total the page showed for that method.
- **Hold-first, the hold kept while a payment can still succeed.** A link is ours by its PaymentRecord or its signed note (above). Its state is read from the link **and** its charges (`beamPaymentState`, first match wins): refunded (a VOIDED/REFUNDED link with at most one successful charge) > any SUCCEEDED charge = paid (every one listed; a second one is a double charge) > a PAID link with no charge listed yet = paid > ACTIVE = open or processing (an ACTIVE link 2 minutes past its expiry is disabled by us) > EXPIRED/DISABLED with a PENDING charge = processing inside `BEAM_PENDING_GRACE_MINUTES` (20) after the expiry, then expired + `unconfirmed` while that charge is under 24 hours old > expired > anything unknown = processing. So a PromptPay QR, a 3-D Secure step or a wallet approval still pending at the 30-minute deadline keeps the hold for the grace, and a hold is never released on an answer we don't understand.
- **"Don't pay again", never a second payment.** A payment still unconfirmed at the bank when its grace ended is released (its unit goes back on sale, the owner gets "Beam payment still pending: hold ... released"), but status and abandon answer it `pending` / `unconfirmed`: the return page says "Waiting for your bank or wallet to confirm" with no Try again, and a new Pay in that tab goes to the return page instead of a second link (when that check itself fails, no new Beam link opens for `attemptPayableMinutes`, 53 minutes by default).
- **A late success is always found.** Beam sends no expiry event and documents very late `charge.succeeded`s, so every sweeper run scans Beam's payment-link charges itself (72 hours, a 7-day pass every 6 hours), reads every open link, and watches released links for `BEAM_LATE_WATCH_DAYS` (7; a released link whose last reading showed a PENDING charge for up to 30 days, `BEAM_PENDING_WATCH_DAYS`). A payment that succeeds after its hold was released is the CRITICAL "URGENT: paid booking ... needs attention" (the guest PAID but the hold is CANCELLED): re-book the guest if the unit is free, otherwise refund in full (owner decision 3; nothing is refunded automatically).
- **The webhook acknowledges only what is durable.** The paid marker and the paid-but-unconfirmed entry are written before the 200; only a failure to write them answers 503 (Beam retries).
- **The release guard.** Every Beam release re-reads the link and its charges inside the release lock, right before the Cloudbeds cancel: a charge that became payable or paid since keeps the hold. Beam's 404 for a link of ours counts as "can never be paid" only for a link created under this `BEAM_MERCHANT_ID` whose expiry plus the grace is over; before that (or for another merchant's link) the hold is kept.
- **Refunded before confirmation, mismatches and double charges go to the owner, never automatically anywhere.** A refunded link is never confirmed or released (CRITICAL "needs attention": do not confirm, cancel by hand); a link that names another booking or merchant, or whose amount differs, is CRITICAL "needs attention"; every extra successful charge on a link is "URGENT: guest charged twice" (refund it, never record it); a refunded link with two or more successful charges is the CRITICAL "... check in Lighthouse which charges were refunded".
- **Refunds stay manual.** No code refunds anything (section 8). The "PAID via Beam" note names the charge, the method and its refund path, and so does the "New direct booking" alert.
- **One neutral fee item per Beam mode.** beam-live posts the Cloudbeds item `msv-payment-processing-fee-beam` ("Payment processing fee", note "Online booking payment processing fee (card or e-wallet), paid via Beam."), beam-playground `msv-payment-processing-fee-beam-test` ("TEST - Payment processing fee"); Stripe's items are never used for Beam money. No Beam text names Stripe.
- **Beam money under Beam's own Cloudbeds method.** `postPayment` uses `CLOUDBEDS_BEAM_PAYMENT_METHOD` (outside live `CLOUDBEDS_BEAM_TEST_PAYMENT_METHOD` when set), the exact method value of the custom "Beam(website)" method for card, e-wallet and PromptPay money alike; no default, built-in methods refused, and a value equal (ignoring case) to a set `CLOUDBEDS_STRIPE_PAYMENT_METHOD` or `CLOUDBEDS_STRIPE_TEST_PAYMENT_METHOD` refused (the problem names the Stripe variable).
- **A Beam outage never strands a guest.** Three failed payment-page creations in a row (inside 5 minutes) pause Beam checkout for 5 minutes, refused before anything is held (the guest is sent to the classic page or WhatsApp). A create Beam answered 429 is not counted (a rate limit is not an outage); 20 answers 429 in an hour tell the owner instead.
- **Previews can't write fake holds into the shared Redis.** A Beam mode without the Cloudbeds booking key (the fake Cloudbeds) runs only locally, on an in-memory store.
- **Either provider can be switched off without losing a payment.** After `BOOKING_PAYMENT_PROVIDER` moves from beam to stripe (or demo), the Beam drain keeps finishing Beam payments (webhook, sweeper, return page, Cancel) while the Beam variables are set; the Stripe drain does the same the other way (section 6).

**Pay, Cancel and Back (Stripe)**
- Pay sends the cart (never prices) plus the guest details in the request body, then follows the redirect only if it is our origin or `checkout.stripe.com` (or Beam's hosts) - `isAllowedPaymentRedirect`.
- Stripe's back link lands on `<page>?resume=payment&reason=cancelled&ref&t`. The page reads `ref`/`t` on the server, POSTs `/api/booking/abandon` at once and keeps Pay disabled ("Checking your earlier payment...") until it answers: `paid`/`pending` → the return page (never a second charge); `released`/`closed` → Pay creates a new hold.
- The browser's own Back button from Stripe: the tab remembers its last attempt (ref + signed link token + start time, no personal data). The next Pay first abandons that attempt the same way, so the old hold never blocks the new one.
- If that check fails (Stripe or our server unreachable), Pay does **not** open a second payable Stripe session while the earlier one could still be paid (33 minutes from its start): the guest sees "We couldn't check your earlier payment attempt just now ..." with WhatsApp and can press Pay again a minute later. After 33 minutes the earlier session has certainly expired at Stripe and Pay carries on. A session Stripe says does not exist counts as closed.
- **Beam (hold-first, design S5.1)** runs the same flow: Beam's Cancel button lands on the same `?resume=payment&reason=cancelled&ref&t` (abandon disables the link and releases the hold), the tab remembers its Beam attempt and the next Pay abandons it first. `pending` includes a payment the bank has not confirmed yet and a released hold whose link was not read again: the return page reads the link and tells "expired" from "still being confirmed". If the check fails, no new Beam link is opened for `attemptPayableMinutes` (the 30-minute link + `BEAM_PENDING_GRACE_MINUTES` + 3 = 53 by default), because a PromptPay or 3-D Secure payment can still succeed inside the pending grace. The tab's Beam attempt keeps that window, so after a switch to Stripe (`BOOKING_PAYMENT_PROVIDER=stripe`) the Stripe page also waits up to 53 minutes for a Beam attempt it can't check before it opens a Stripe payment (round 7). Beam's return page checks after 2 s, then each wait x1.5 up to 15 s, for 15 minutes (Stripe: ~3 s for 3 minutes; the demo: its old backoff). The guest step says the details go to our reservation system only (Beam gets no name, email or phone) and promises no receipt.
- Errors: `price_changed` without a quote (Cloudbeds priced the hold differently; it was cancelled) refreshes the search once and offers WhatsApp - never an automatic retry. `test_mode_restricted` offers "Change dates" / "Edit guest details". `terms_changed` offers "Refresh page" (see Terms above). A stay rule (minimum stay, closed to arrival...) names the rule.

## 2. Environment variables

Set these in Vercel under **Project → Settings → Environment Variables**. Scope live secrets to **Production** only and mark them sensitive. **Redeploy afterwards**, because changes only apply to new deployments.

**Variables marked "Not needed in Vercel" have safe defaults: leave them out, don't add them with an empty value.** This covers the three DIRECT variables (`BOOKING_DIRECT_PROMO`, `BOOKING_PROMO_CODE`, `CLOUDBEDS_PROMO_CODE`) and the two automatic-discount variables (`BOOKING_AUTO_DISCOUNTS`, `BOOKING_AUTO_DISCOUNT_PLANS`). With none of them set (an empty value is read as not set), the own engine sells the Direct rate for the code `DIRECT`, using Cloudbeds' promo code `Direct`, the plan of **any other promo code** set up in Cloudbeds for that code (owner decision, 2026-10-07: e.g. `LONGSTAY` for "Long term"; codes need no variable at all, the engine reads them from Cloudbeds' rate plans), and, with no code, the plans whose public name starts with "Last minute", "Long term" or "Early bird" and carry no promo code (owner decision, 2026-10-07; early bird plans included, with no setting). Add one only to change that: `BOOKING_DIRECT_PROMO=off` after a "DIRECT bookings blocked" or "Code <CODE> bookings blocked" alert (it switches off every code), `BOOKING_AUTO_DISCOUNTS=off` after an "Automatic discounts blocked" alert, `CLOUDBEDS_PROMO_CODE` if the plan's code is changed in Cloudbeds, or `BOOKING_AUTO_DISCOUNT_PLANS` to sell other plans automatically (or fewer).

**Other promo codes (owner decision, 2026-10-07: "Long term" behind `LONGSTAY`, and any code the owner sets up).** What the code relies on, and what is still open:
- `getRatePlans` asked without a room type lists every promo plan with its `promoCode` (live, Honeymoon: "Direct booking rate" with `Direct`, "SabaiTravel2026" with `SabaiTravel2026`; `includePromoCode` defaults to true). - `getAvailableRoomTypes` asked with a code returns only that code's rows (live for `Direct`, Stage B 2026-10-07), so the search asks plain and with the code, as for DIRECT.
- **Still open (Stage B case 28):** the same for `LONGSTAY`; that `postReservation` prices the plan's `roomRateID` + `promoCode` at the plan's rate (proven for the Direct rate); whether Cloudbeds offers the plan's rows for a stay below its minimum stay (the checkout refuses such a hold either way), and how it answers when it does not: success with no rows, or a refusal of the code (`success:false`, e.g. "Invalid promo code") - the engine takes both as "no rows for the code" (a refusal logs `cloudbeds_promo_answer_refused` with Cloudbeds' message), so the guest sees the base rates and "doesn't apply to these dates", never the 503; and that the plan is open to the own page's source (4.B step 8).

**Native Stripe reference (research note, Oct 2026).** Cloudbeds' `postReservation` has two Stripe-only fields.
- `cardToken`: a Stripe **Customer** id. Cloudbeds saves the card for later charges.
- `paymentAuthorizationCode`: the **Charge** id behind a PaymentIntent. Cloudbeds treats it as the deposit.

These fields have limits:
- They exist only **when the reservation is created**, and `paymentAuthorizationCode` requires `cardToken`. So the charge must exist before the reservation. That is pay-first, the opposite of our hold-first flow.
- There is no equivalent field on `postPayment` or `putReservation`.
- They require a Stripe Customer with an attached payment method, which Checkout in payment mode does not create.

Sources:
- https://developers.cloudbeds.com/docs/pass-stripe-tokens-to-cloudbeds
- https://developers.cloudbeds.com/reference/post_postreservation-2

We therefore use the documented external-payment path: `postPayment` + `putReservation`, as in https://developers.cloudbeds.com/docs/booking_engine_payment.

### D. Sweeper (required for live)

Set `BOOKING_SWEEP_SECRET` (32 random characters) - live payments stay locked without it. Vercel Hobby crons run once a day, so call the sweeper every 10 minutes from the droplet's cron:

```
*/10 * * * * curl -fsS -X POST -H "Authorization: Bearer $BOOKING_SWEEP_SECRET" https://magicsamui.com/api/booking/sweep >/dev/null
```

On Vercel Pro, a `vercel.json` cron works too. It sends `Authorization: Bearer $CRON_SECRET`; the sweeper accepts `CRON_SECRET` **and** `BOOKING_SWEEP_SECRET` when both are set, so the droplet cron and a Vercel cron can run side by side.

Each run answers counts only, e.g. `{"ok":true,"mode":"stripe-live","released":0,"openHolds":0,"paidUnconfirmed":0,"pruned":0,"undeliveredAlerts":0,"cloudbedsOk":true,...}`. **`paidUnconfirmed` must be 0**: anything else is a paid booking whose Cloudbeds confirmation keeps failing (the owner is alerted; never cancel it). **`openHolds` must be 0 before any change of provider or Stripe keys** (section 6, drain). While a Beam config exists (Beam active, or the Beam drain after a switch away from it) the answer also carries `runs[]`, one entry per provider (`{"provider":"stripe",...}`, `{"provider":"beam",...}`), and its top-level counts are the **active provider's run only**: a drain's open holds appear only in `runs[]`. Then **every** `runs[].openHolds`, `runs[].errors` and `runs[].paidUnconfirmed` must be 0 before any provider's variables or keys change. Each run is `{provider, mode, ok, error?, skipped?, ...its counts}`; the Beam run also carries `links`, what Beam's step 1 read: `open` (links-open), `scanned` (links named by the charge scan), `watched` and `pendingWatched` (the late watch and the pending watch), `watchedRead` (released links read this run), `watchCovered` (late-watch links whose whole life the completed charge scan covered, so not read) and `watchDeferred` (older late-watch links not read this run because a good reading of them is under an hour old: a released link older than the charge scan is read about once an hour, so a late success on it with its webhook lost is found within about an hour). With Beam as the active provider, `links` is at the top level too, and Beam's run goes first. The request answers **502** when any run failed, was skipped for time or could not list Cloudbeds (every run is still attempted); `error` is the first failed run's (`payments_unavailable`: its payment check failed; `cloudbeds_unavailable`; `out_of_time`; `sweep_failed`). When the run could not list Cloudbeds reservations it answers **HTTP 502** `{"ok":false,"error":"cloudbeds_unavailable",...}`, so `curl -f` exits non-zero (the droplet's cron mail shows it), and it does not count as a sweep. In live, checkout emails "The booking sweeper has not run recently" when no sweep with a working Cloudbeds side has run for 30 minutes.

## 6. Cutover and rollback

1. **Soft launch.**
   - Only after the Stage C go/no-go, including the legal items (Owner TODO 4 answered in writing, 4.F referral saved; TODO 1 closed on 2026-10-06).
   - Keep `BOOKING_ENGINE=cloudbeds`.
   - Run live Stripe on the unlinked `/booking-preview` for 1–2 weeks (Standard Rate, the Direct rate with code DIRECT, a code plan such as "Long term" with `LONGSTAY`, or an automatic discount plan such as an "Early bird..." one; 100% payment). The first real booking on "Last minute 10% off" is Stage C step 8. These are real bookings: gtag.js loads there in stripe-live, so they reach GA4 and the Ads import.
   - Send the link to a few WhatsApp guests.
2. **Swap.**
   - Set `BOOKING_ENGINE=own` and redeploy. `/booking` then renders our engine, but only while stripe-live is fully unlocked.
   - The Cloudbeds engine moves to `/booking/classic` (noindex), linked under the page title.
   - Return URLs then use `/booking/return`; the homepage date picker becomes the booking page's search bar. The "Code DIRECT" perks and the "best rate when you book direct" wording stay while the own engine honours DIRECT; with `BOOKING_DIRECT_PROMO=off` they are replaced automatically on the homepage, `/booking`, the site-wide meta description and the seven language pages (not `public/llms.txt` or the ads: edit those by hand, section 4.G item 4).
   - `?promo=DIRECT` from links applies the Direct rate (with the flag off: the note linking `/booking/classic`).
   - Do section 4.G (Google Ads) first.
   - Check after the redeploy: `/booking` shows our engine with no preview banner, `/booking/classic` loads the Cloudbeds engine, the homepage search bar lands on `/booking` with the dates filled in, and Lighthouse CLS on the homepage is not worse. (Our homepage search bar is taller than the Cloudbeds widget - 240 px vs 98 px on phones, 116 px vs 106 px from 768 px - so the content below starts lower; there is no layout shift.)
3. **Run both engines for 2+ weeks.** Watch for double-counted GA4 purchases, "paid but not confirmed" alerts and holds stuck in `not_confirmed`. In Google Ads → Goals → Conversions, check that Purchase keeps receiving conversions from the GA4 import after the swap (and is not double-counted by any direct Cloudbeds Ads tag, section 4.G).
4. **Rollback.**
   - **Set `BOOKING_ENGINE=cloudbeds` and redeploy.** That is the rollback for the engine swap: the new deployment keeps the live Stripe keys, webhook, sweeper and `/booking/return`, so in-flight sessions still confirm or release their holds.
   - **Change nothing else.** Never change `BOOKING_PAYMENT_PROVIDER` or the Stripe keys as part of an engine rollback: keep the Stripe webhook and the sweeper running so in-flight sessions still confirm or release their holds. (Switching the provider from Beam back to Stripe is its own rollback, item 8: both drains keep every in-flight payment.)
   - **Avoid Vercel's "Instant Rollback" for this.** It brings back an old deployment exactly as it was built, with its own code **and its own environment variables**. A deployment from before this branch was merged has no `/api/stripe/webhook`, `/api/booking/sweep` or `/booking/return`; a Stage B deployment runs on Stripe **test** keys and the test webhook secret. Either way paid guests land on a 404 or an error page, every live webhook fails, and unpaid holds keep units off the OTAs until someone rolls forward. If you use it anyway, pick only the **last production deployment built with the same live Stripe, Cloudbeds and Redis settings** - never one from before the merge, never a Stage B one. While an instant rollback is active, Vercel does **not** put new git pushes live (e.g. content commits) until you press **"Undo Rollback"** in the Deployments view.
5. **Emergency stop** (either provider). Set `BOOKING_ALLOW_LIVE_PAYMENTS=false` and redeploy.
   - New checkouts lock at once.
   - `/booking` falls back to Cloudbeds automatically, because the own engine requires live payments to be unlocked.
   - A guest whose page was loaded before the stop and presses Pay reads "Online payment is paused - No payment was taken" with "Book on our classic booking page" as the main action and WhatsApp; both Pay buttons (in the page and the phone bar) turn into a disabled "Online payment paused", and screen readers hear "Online payment is paused. Nothing was charged." instead of the stale "taking you to Stripe". The live `/booking/return` never shows a "demo mode" note on an unverified view during the stop.
   - Bookings already paid still get confirmed, and abandoned holds still get released. The webhook, sweeper, status and abandon endpoints use `getFulfilmentConfig`, which ignores only this flag (on Beam also `CLOUDBEDS_SEND_STATUS_EMAIL`, the other checkout-only condition).
   - Their GA4 `purchase` is still recorded: gtag.js keeps loading on `/booking-preview/return` (the soft-launch return page) while live Stripe or Beam payments are being finished, and `/booking/return` is tracked as usual.
   - The preview's search (`/api/booking/availability`) answers 503 while payments are locked on production, so a locked page never spends the shared Cloudbeds read key.
6. **Changing the provider or the Stripe keys (drain), or removing a provider's variables.** A Stripe session lives 30 minutes and a delayed PromptPay payment can confirm later, so (a plain switch of `BOOKING_PAYMENT_PROVIDER` between `beam` and `stripe` with both providers' variables kept is safe without it, item 8; this procedure is for changing keys and for removing a provider):
   1. Stop new holds: `BOOKING_ALLOW_LIVE_PAYMENTS=false` (live) or remove the test access key / unlock cookie (Stage B), and redeploy.
   2. Wait at least **1 hour**.
   3. Call the sweeper by hand and confirm it answers `"openHolds":0` and `"errors":0`. When the answer has `runs[]` (a Beam config exists), confirm it for **every** entry of `runs[]` (`openHolds`, `errors` and `paidUnconfirmed` all 0): the top-level counts are the active provider's only.
   4. In Cloudbeds, search for reservations whose third-party id starts with `MSV-` and status "Confirmation pending"; cancel any left over by hand (none should be).
   5. Only then switch `BOOKING_PAYMENT_PROVIDER` or the keys, and redeploy.
   - Safety net if this is skipped: while the Stripe key and webhook secret are still set, the webhook, sweeper, return page and abandon endpoints keep finishing Stripe sessions even after `BOOKING_PAYMENT_PROVIDER` is switched to `beam` or `demo` (drain mode, log `stripe_drain_mode`). So **keep the Stripe variables for at least 3 days** after switching the provider. Swapping test keys for live keys cannot drain test sessions (a live key cannot read them) - hence the procedure above before Stage C.
   - **Removing the Beam variables** (base, keys, `BEAM_WEBHOOK_HMAC_KEY`) ends the Beam drain: the webhook then answers 503 and no sweeper run reads Beam any more. Remove them only after the procedure above **and** once the Beam run's `links` shows `open` 0 and `pendingWatched` 0 for `BEAM_LATE_WATCH_DAYS` (7 days) after the last Beam booking; then check Lighthouse for late payments by hand for 30 days.
   - A typo in the payment variables (for example a misspelt `BOOKING_PAYMENT_PROVIDER`; the log shows `config error: payment_misconfigured - missing: ...`) stops checkout, and the status and Cancel endpoints answer 503 "not configured" for Stripe bookings, as before. While the Beam drain can be built - the Beam variables (base, both keys, the webhook key) set and, on Vercel, the Cloudbeds booking key with its numeric property id, Redis and live Cloudbeds data - Beam bookings already started still get their status, their Cancel and their return page from the Beam drain, and the webhooks and the sweeper keep finishing the payments of each provider whose variables are set (its drain). Fix the typo and redeploy. A lock (`live_payments_locked`) never takes this path.
7. **Beam go-live** (design rollout; never without the owner's explicit approval of S7.1).
   1. The owner pushes `beam-live` (4.H step 1) and merges the PR to `main` with `LIVE_FULFILMENT_READY.beam` still `false`. Nothing changes for guests: production stays on Stripe, has no Beam variables, and no Beam drain exists. Watch Stripe for 24 hours (section 5, "Stripe regression after the merge").
   2. With the owner's explicit approval, S7.1 (the flag flip, the one sanctioned change of a golden record) is merged and deployed. Still nothing changes: the provider is `stripe` and production has no Beam variables.
   3. Only now the Production Beam setup of 4.H step 10 (the Lighthouse Production webhook, the Production Beam variables, provider still `stripe`), with its checks: an unsigned POST to `/api/beam/webhook` answers 401, and for 24 hours the sweeper's answer lists a `beam` run without errors.
   4. Go-live window: `BOOKING_PAYMENT_PROVIDER=beam` and redeploy. `/booking` shows the own engine with the method choice (while `BOOKING_ENGINE=own` and beam-live is fully unlocked; otherwise the soft-launch `/booking-preview`). Run Beam Stage C, then watch the alerts, the sweeper's answers and Lighthouse against Cloudbeds for 48 hours.
8. **Rollback from Beam to Stripe (the provider switch).** `BOOKING_PAYMENT_PROVIDER=stripe` and redeploy (about 1-2 minutes; never Vercel's Instant Rollback, item 4). This is an allowed rollback because both providers drain:
   - **Keep every Beam variable** (base, keys, `BEAM_WEBHOOK_HMAC_KEY`, `CLOUDBEDS_BEAM_PAYMENT_METHOD`): the Beam drain keeps confirming or releasing the Beam links already handed out (the webhook, the sweeper's `beam` run, the return page and Cancel; log `beam_drain_mode` once). The same holds the other way: switching back to `beam` keeps finishing Stripe sessions while the Stripe variables are set (`stripe_drain_mode`).
   - A guest whose page still shows Beam's 3% total and presses Pay gets "the price has changed" with the Stripe quote (5%), nothing held. A tab with a Beam attempt it can't check waits up to 53 minutes (or the guest messages us) before it opens a Stripe payment.
   - A Beam outage during the redeploy is handled by the circuit breaker: after 3 failed payment pages Beam checkout pauses for 5 minutes, nothing is held, guests are sent to the classic page or WhatsApp.
   - `/privacy` and `/legal` keep naming Beam while the Beam drain exists, and Stripe again (section 1, "Privacy and legal with Beam").
   - Before any provider's variables or keys change afterwards: every `runs[].openHolds`, `errors` and `paidUnconfirmed` must be 0 (item 6).
9. **Rolling the code back to before the Beam merge** (a revert, or an Instant Rollback to a pre-Beam deployment). First **disable the Lighthouse Production webhook, or remove `BEAM_WEBHOOK_HMAC_KEY`**: production `main`'s old route acknowledges every signed event, so Beam would never retry an event that old code did not process (with the webhook disabled or the key removed it answers 503 and Beam keeps retrying, up to 10 times). Then handle the open Beam holds by hand: the old code never touches a `-B` hold, so search Cloudbeds for Source Reservation IDs ending `-B` with status "Confirmation pending" and check each link in Lighthouse - paid: record the payment under Beam(website) and confirm; not paid: disable the link in Lighthouse and cancel the reservation. After rolling forward again, the sweeper's 7-day charge scan finds what was paid meanwhile (a payment whose hold was cancelled raises the CRITICAL "needs attention"). Since S4.7 the merged code never acknowledges blindly: a deployment with the key but no Beam deps (no Beam config, no Beam drain) answers 503.

Their holds are kept and each raises the CRITICAL "URGENT: Beam payment link {id} for booking {ref} belongs to another Beam merchant"; released links in the late watch (7 days) or the pending watch (up to 30 days) can no longer be checked for a late payment. So **never change `BEAM_MERCHANT_ID` while Beam links are open or watched** (section 2; the Upstash sets `msv:{scope}:beam:links:open`, `…:links:watch` and `…:links:pending`, scope `beam-live` in live). To switch merchants: set `BOOKING_PAYMENT_PROVIDER=stripe` first (redeploy), wait until the `beam` run's `links.open`, `links.watched` and `links.pendingWatched` are all 0 (and its `openHolds` 0): about `BEAM_LATE_WATCH_DAYS` (7 days) after the last Beam booking, up to 30 days while a released link still has a pending charge - otherwise every link still watched raises the merchant CRITICAL, every sweeper run reports `errors` for up to 30 days and "could not be read for 60 minutes" repeats. Then change the merchant's variables (and the Lighthouse webhook and its HMAC key), switch back, and check the **old** merchant's Lighthouse for late payments for 30 days.
11. **When the sweeper can't check Beam.**
   - Beam refusing the sweeper's unfiltered charge list (a 4xx other than 429) is told once per HTTP status per day ("Beam refused the sweeper's payment scan", log `beam_scan_refused`); the sweeper then reads every open and watched link on every run. Ask Beam whether the list is available (question 8).
   - A Beam step 1 that fails (the scan answered 5xx or could not finish, or a link whose record is gone could not be read) fails the `beam` run (`error` `payments_unavailable`, HTTP 502) and **keeps every Beam hold** until a run succeeds; paid bookings already known are still retried and stored urgent alerts re-sent. The 3rd failed run in a row: "The booking sweeper cannot check Beam payments".
   - One link that can't be read keeps its own hold (the unit stays blocked) and is told after 60 minutes ("Beam link {id} could not be read for 60 minutes"); one that can't be disabled is told after 60 minutes too ("... could not be disabled for 60 minutes"): disable it in Lighthouse.

## 7. Alerts

Alerts are emails to `BOOKING_ALERT_EMAIL` (default info@) in live mode, and log lines (`alert_<severity>`) otherwise (`BOOKING_ALERTS_IN_TEST=true` emails them in test mode too). They never contain guest personal data: only the ref, the Cloudbeds reservation id, dates, amounts and error codes.

Delivery (`src/lib/booking/alerts.ts`):
- Sent **after** the response (`next/server` `after()`), so a slow mail relay never delays a checkout or a webhook. Relay and SMTP fallback each get 8 s.
- Repeats of the same alert are suppressed for 6 hours **only once delivered**: a failed send logs `alert_send_failed` and frees the key, so the next occurrence tries again (a send killed mid-way frees it after 2 minutes).
- **Critical** alerts are stored in Redis before sending and removed once delivered. Every sweeper run re-sends the undelivered ones (marked "Re-sent by the booking sweeper") for up to 7 days and reports `undeliveredAlerts`. If that number stays above 0, mail is down: check the droplet relay and the Gmail app password, and read the alert in Redis (`msv:live:alerts:pending`; a test deployment's are under `msv:stripe-test:…`; Beam's under `msv:beam-live:…` and `msv:beam-playground:…`) or the Vercel logs.

### Beam alerts (design S4.1-S4.8)

Every alert of the table above is also sent for Beam bookings, in Beam's words: "Beam payment link {linkId}" (or "Beam link {linkId}"; the id Lighthouse shows, never our Redis key) where Stripe says "Stripe session", "Beam webhook retries", `CLOUDBEDS_BEAM_PAYMENT_METHOD` (outside live `CLOUDBEDS_BEAM_TEST_PAYMENT_METHOD`) and the custom 'Beam(website)' method in "Online bookings stopped: the Cloudbeds payment method is not set up" (whose problem line also refuses a Beam value equal to a set Stripe method variable, naming it) and in "URGENT: paid booking …: Cloudbeds refused to record the payment", the method's refund path in "needs attention" and in "New direct booking". The two Stripe-only ones ("Stripe webhook: signatures are being rejected", "Booking stopped: Stripe could not create the payment page") have Beam counterparts below. A mail's subject reads `[Booking {severity}] {subject}`, with the mode in front outside live (`[beam-playground] [Booking critical] …`). "Once" means a set-once marker per link or charge (`msv:{scope}:beam:reported:…`, kept 708 days); critical alerts are stored and re-sent by the sweeper until a mail goes out, as above.

## 8. Refund runbook

Neither the Cloudbeds API nor our code refunds anything. Refunds are always manual, in two systems: the payment provider and Cloudbeds. Points 1-6 are Stripe's (and points 3 and 4 apply to Beam too); Beam's own steps, including the bank transfers, follow under "Beam refunds".

1. **Stripe.**
   - Dashboard → Payments → find the payment by searching the `MSV-…` ref (it is in the description and metadata) → **Refund**, full or partial.
   - **PromptPay refunds** need the guest's bank account: Stripe emails the guest to collect it (https://docs.stripe.com/payments/promptpay).
2. **Cloudbeds.**
   - Open the reservation (Stripe metadata `msv_cb_reservation_id`) → Folio.
   - Record the refund as a **negative adjustment or refund entry** by hand. Voiding a recorded payment through the API is unreliable and not used.
   - Cancel the reservation if the stay is cancelled, so the unit goes back to the OTAs.
3. **The guest's "Payment processing fee" line.** The cancellation policy every guest agrees to (`HOUSE_POLICIES.cancellation`) says: "The payment processing fee is refunded only when the whole stay is refunded." The tiers are the owner's (decided 2026-10-06, Owner TODO 5):
   - **Cancelled 60 days or more before arrival** (or our fault): a **full refund**, the full amount paid **including** the fee line.
   - **Cancelled less than 60 days before arrival**: refund **50% of the stay** (half of the rooms total) and **keep the fee**.
   - A no-show is not covered by the agreed text (open, Owner TODO 5): ask the owner before refunding one.

   The "PAID via Stripe" note (and the session's `msv_terms`) says which terms version the guest agreed to: checkout takes only the version the guest's page showed (a tab opened before a terms change is asked to refresh, review and tick again before anything is held), so it is the version the guest saw. Record the same split in the Cloudbeds folio (room refund vs fee item). If the owner decides otherwise (Owner TODO 4), change the policy text and `POLICY_VERSION` first - guests are only bound by what they agreed to.
4. **Google Ads.** After a **full** refund, retract the booking's conversion: **Google Ads → Goals → Conversions → Uploads → Conversion adjustments**, a retraction for the Purchase action with the Cloudbeds reservation id as the transaction id (for a partial refund, a restatement with the new value). Otherwise refunded bookings stay in conversion value and Smart Bidding.
5. **Currency.** Checkout Sessions pin Adaptive Pricing off, so every payment and refund is in THB. If a payment ever shows a presentment currency other than THB (Adaptive Pricing switched on for an old session, or a Stripe default change), refund it in Stripe as usual - Stripe refunds in the guest's currency at the original rate - and record the THB amount in Cloudbeds.
6. **Our own Stripe cost.** Stripe does not return its own processing fee to us on refunds. Each dispute costs ฿500, and for prepaid stays the dispute window starts on the stay date, so keep the booking evidence.

### Beam refunds (owner decisions 3 and 4; design staff guidance)

No code refunds anything on Beam either: refunds are made by hand in **Beam Lighthouse** or by **bank transfer**, then recorded in Cloudbeds by hand. Beam can refund only cards, PromptPay, Alipay and WeChat Pay (and card instalments, which our links don't offer), and only **cards in part**; LINE Pay, TrueMoney and ShopeePay can't be refunded through Beam at all.

1. **Find the payment.** Lighthouse → **Payments**: search the booking reference (`MSV-…`) or the charge id printed in the Cloudbeds note "PAID via Beam {charge id} ({method}, THB x). Refund path: …". The note (and the "New direct booking" alert) already says the method and where its refund goes.
2. **The cancellation tiers** are the same as on Stripe (point 3 above: 60 days or more before arrival, or our fault, a full refund including the "Payment processing fee" line; less than 60 days, 50% of the rooms total and the fee is kept):

   | Paid by | Full refund | 50% refund |
   |---|---|---|
   | Card | Lighthouse → the charge → **Refund** (full) | Lighthouse → the charge → **Refund** → the partial amount |
   | Thai PromptPay QR | Lighthouse → the charge → Refund (full) | **bank transfer** (Beam refunds PromptPay only in full) |
   | Alipay, WeChat Pay | Lighthouse → the charge → Refund (full) | **bank transfer** (until Beam confirms partial refunds in Lighthouse, question 12) |
   | LINE Pay, TrueMoney, ShopeePay | **bank transfer** (Beam can't refund them) | **bank transfer** |

3. **Bank transfer** (owner decision 4; who pays it, from which account and who bears international fees is the owner's decision, section 10):
   1. Ask the guest on WhatsApp or by email for their bank details (Thai guests: a bank account or PromptPay ID; abroad: IBAN + SWIFT, or a transfer service the owner uses). **Never ask for card numbers.**
   2. Transfer the amount from the business account and keep the slip.
   3. In Cloudbeds, on the reservation's folio, add a negative adjustment "Refund {50% | full} by bank transfer {date}, slip {transfer ref}" for the amount, and a note with the same text.
   4. Cancel the reservation if the stay is cancelled, so the unit goes back to the OTAs.
   5. Google Ads: restate the conversion (partial) or retract it (full), point 4 above.
4. **After any Beam refund.** The "Beam refund done for booking … (THB x)" alert means Beam accepted it (the guest's bank may take days). Record it in Cloudbeds by hand (a negative adjustment or refund entry on the folio; Beam's refund never changes the folio), cancel the reservation if the stay is cancelled, and retract (full) or restate (partial) the Ads conversion - unless the alert's second line says the refunded charge was never recorded in Cloudbeds: the extra charge of a duplicate payment (item 6: nothing to record, the booking and its conversion stand) or a booking the engine never confirmed (items 5 and 7: nothing to adjust unless the payment was recorded by hand; make sure the reservation is cancelled). Refunds are paid from the **available Beam balance** (PromptPay settles T+1, cards T+3): if Beam refuses for a low balance ("Beam refund FAILED for booking …"), retry the next day or pay by bank transfer. A refund alert that names only the booking reference ("the reservation of booking … (search the booking reference in Cloudbeds)") and says "method not known" comes when our charge index for that payment is gone: find the reservation by its reference and the method in Lighthouse.
5. **Late payment** (the URGENT "needs attention": the guest PAID but the hold is CANCELLED; owner decision 3). If the unit is still free for those dates, re-instate or re-book the guest in Cloudbeds and record the Beam payment on that folio under the Beam(website) method; otherwise refund the **full** amount in Lighthouse (bank transfer for LINE Pay, TrueMoney or ShopeePay) and tell the guest. Nothing is refunded automatically. For a payment that was still pending when its hold was released ("Beam payment still pending: hold … released"), this URGENT alert can come for 30 days after the release (`BEAM_PENDING_WATCH_DAYS`); a success after that is reported only by Beam's webhook, so check Lighthouse against Cloudbeds now and then.
6. **Duplicate charge** ("URGENT: guest charged twice"): the charge the alert names as recorded stays; refund the extra charge in full in Lighthouse (bank transfer for LINE Pay, TrueMoney or ShopeePay). Do not record the extra charge in Cloudbeds and do not cancel the booking.
7. **Refunded before the booking was confirmed** ("REFUNDED at Beam before the booking was confirmed"): do not confirm; check that the folio shows no payment and cancel the reservation by hand.
8. **Paid with the other method group** ("Booking …: paid by … on a … payment page"): the booking stands. Collect or waive the card fee a PromptPay page did not charge; refund a fee a card page charged on a PromptPay payment by bank transfer, unless the guest agreed to keep it.
9. **Chargeback** ("URGENT: chargeback on Beam payment for booking …", or "… on a Beam payment" when it matches no booking): collect the evidence - the agreed terms version in the PAID note, the Cloudbeds reservation and its folio, the guest's messages, the check-in records - and answer Beam's dispute process (how Beam notifies and handles disputes is question 14); record the outcome on the folio. A card dispute on a prepaid stay can come months after the payment, so keep the booking evidence (our Beam records and charge index are kept 708 days, so a late refund or chargeback still finds its booking).
10. **Currency and our cost.** Every Beam payment and refund is in THB. Beam's processing fee and its VAT come only with the `transaction.created` webhook (log `beam_transaction`: gross, fee, VAT, net): reconcile those lines against Lighthouse's reports. Whether Beam returns its fee on a refund is not documented (assume not).

## 9. Known limits

- A hold blocks the unit for up to ~31 minutes if the guest walks away without pressing Cancel (Stripe's minimum session life is 30 min).
- **Hold-inventory abuse.** Every Pay creates a real Cloudbeds hold before any payment, so someone scripting checkouts with made-up details could keep units off the OTAs. Brakes in code: at most 8 open holds at once (then new checkouts are refused with an alert), at most 5 holds per guest (IP + email) and 15 per IP per 40 minutes (so guests sharing hotel Wi-Fi or a carrier's NAT don't lock each other out; a refused guest is told how long to wait and offered `/booking/classic` and WhatsApp), plus the per-instance request limiter. A determined attacker with many IPs could still block units for 40 minutes at a time; if the "too many unpaid holds" alert ever fires, add a bot check (e.g. Cloudflare Turnstile) before the hold step.
- An unclear `postReservation` answer (timeout/5xx) can leave a reservation that blocks the unit until the sweeper releases it (~40-50 minutes, aged by its intent); the guest is told to retry in a minute or message us.
- An unclear `postPayment` answer delays the confirmation by up to 10 minutes (the return page shows "Payment received - confirming"); the payment is never posted twice.
- Stays above THB 999,999.99 can't be paid online in one payment (Stripe's 8-digit limit); the guest is sent to WhatsApp before anything is reserved.
- Without a Cloudbeds confirmation email (`CLOUDBEDS_SEND_STATUS_EMAIL` off; Stripe and, since design S5.3, Beam), the paid return page is the booking confirmation: right under the reference it says "Save or print this page - it is your booking confirmation" with a Print button, it lists the booking terms the guest agreed to (check-in/out, cancellation incl. the fee rule, the damage deposit, children, the free transfer, the house rules, the fee) and the property's address, phone and email, and it offers "Add to calendar". It can't be reopened once the tab is closed (the link's credentials live only in that tab).
- **The own page sells Cloudbeds' base (BAR) rate, the "Direct" plan for the DIRECT code, the plan of any other promo code for that code (e.g. "Long term" for `LONGSTAY`), and the automatic discount plans ("Last minute 10% off", "Early bird..."; any "Long term..." plan without a code) when Cloudbeds offers them for the stay.** The automatic plans are not proven live yet (Stage B case 27 can book only an early bird plan; Last minute only once a real booking inside its window is made: the test guard, Stage C step 8); nor are codes other than DIRECT (Stage B case 28).
- **Any Cloudbeds promo code works on the own page - with these limits** (owner decision, 2026-10-07). A code other than DIRECT costs one extra round trip on the search (the rate-plan index is read before availability, instead of alongside it) and needs `getRatePlans` to answer: when it fails, a search with such a code fails like a search with DIRECT (the 503 "try again"), never quietly sells the base rate. Codes are 1-32 letters, digits, `-` or `_`: a Cloudbeds code with a space or other characters can't be typed on the page. A code is checked against the plans listed for the stay's dates; whether Cloudbeds then offers the plan's rows (minimum stay, its date window) decides whether the guest sees its price ("doesn't apply to these dates" otherwise, also when Cloudbeds refuses the code for the stay with `success:false`: log `cloudbeds_promo_answer_refused`; DIRECT, whose plan has no minimum stay, still treats such a refusal as a failed read), and should Cloudbeds offer a row below the plan's minimum stay, the checkout refuses it with the minimum stay before anything is held. The non-refundable check reads only the plan's public name (as for automatic discounts): a plainly named plan with a non-refundable policy would still be sold under the page's refund terms - give every code plan the base rate's cancellation policy (4.B step 8). One code on several plans is sold per room on the cheapest sellable one, each room labelled with its own plan; the search's "Code X applied: <name>" line names the first plan Cloudbeds lists. The switch is all or nothing: `BOOKING_DIRECT_PROMO=off` turns every code off, DIRECT included (to stop one code, deactivate its plan or change its code in Cloudbeds - never just remove the code from a "Last minute…", "Long term…" or "Early bird…" plan, which would make it automatic). GA4 gets the code as the purchase `coupon` (not the plan's name as `item_variant`, which stays for automatic discounts).
- **Non-refundable is not sold on the own page** (owner decision, 2026-10-07): "Non-refundable 10% discount" has other refund terms than the policy guests agree to on our page (60 days or more: full refund; less: 50%), so it stays on the classic engine only, even if `BOOKING_AUTO_DISCOUNT_PLANS` names it. Selling it would need its own cancellation text on the page first (a code change). Also classic-only: the Breakfast package (+2,000 THB per room per night). Promo-code plans other than Direct are not: they are sold on the own page to guests who type their code (section 1; 4.B step 8), so tick the own page's source on each, else every booking with the code is stopped with the "Booking stopped: Cloudbeds refused the reservation" alert (nothing charged). "SabaiTravel2026" (code `SabaiTravel2026`) has a minimum stay of 150 nights, more than the page's 30, so on the own page its code always answers "doesn't apply to these dates" (or, should Cloudbeds offer its rows anyway, Pay is refused with the minimum stay); those guests book on the classic engine.
- **Price parity with the classic engine (the gap noted on 2026-10-06, updated 2026-10-07).** On 2026-10-06 the own page sold the base rate only, while the classic engine also offered Long term (6% off, 7+ nights: the base rate was about 6.4% dearer), Non-refundable (10% off) and Last minute (10% off). With automatic discounts on, Last minute (and any "Early bird..." plan) is sold on the own page too, with no code (when Cloudbeds offers it for the stay, and only once Stage B case 27 passes; with `BOOKING_AUTO_DISCOUNTS=off` that gap is back). "Long term" (now 26% off, 7+ nights) is behind the promo code `LONGSTAY` since 2026-10-07 (owner decision): code only, never automatic, on both engines. DIRECT gets the Direct rate on both. What remains: a guest willing to book non-refundable pays about 10% less on the classic engine. Non-refundable and Last minute were not offered on the WI-0 dates, so where Cloudbeds offers them is not seen yet. The percentages come from Honeymoon only.
- **DIRECT on the own page is only as good as Cloudbeds' pricing of the hold** (Stage B case 24; a first DIRECT booking went through on 2026-10-07, Stage B log). Until that case passes, a DIRECT booking may be refused ("DIRECT bookings blocked", nothing charged) and the guest sent to `/booking/classic`. Room types without a Direct plan, or dates where it is not offered, get the base rate with a note. A cart mixing a Direct room with such a room sends one reservation-level `promoCode` for both; until case 24 (d) passes, Cloudbeds may refuse or misprice it (refused before payment, nothing charged). The own page still adds its 5% fee on the Direct total, which the classic engine's Card Charging Fee (5%, on the "Website / Booking Engine" source) also does.
- The site's own breakfast plan and add-ons are hidden in Stripe modes, because the base row Cloudbeds holds does not include them.
- **The unit lock covers OPEN holds only.** Our per-unit lock and overlap check see only our own open holds. Once a booking is confirmed it leaves the open-holds index, and from then on Cloudbeds' Split Inventory links are the only guard, against our own later sales too: if, say, Tuxedo 1BR and Tuxedo 2BR were not linked in Cloudbeds, a paid Tuxedo 1BR would not stop our page selling Tuxedo 2BR for the same nights. Hence 4.B step 4 and Stage B tests 10 and 11 in both directions.
- **Paid-but-unconfirmed retries stop after 30 days.** A paid booking's record lives 30 days. After that the sweeper drops it from its paid list and stops retrying and alerting. It is never cancelled, but by then a person must have settled it (the CRITICAL alerts start at once for a refused payment record, otherwise after 2 hours).
- **A single room type without a base row is a log line only.** If Cloudbeds stops sending the base row for every room (for example if the "default" name of the base plan changes), the page shows every room sold out and the owner gets "Online bookings stopped: Cloudbeds returned no base rate for any room" (section 7). If only some room types lose it, those are shown sold out while the others still sell, and the only signal is the info line `[booking] cloudbeds_no_base_rate` per room type: watch the Vercel logs for that tag (or add a log-drain alert on it).
- **Cloudbeds fees added after payment are not seen.** The fee checks run at checkout and at payment. A tax or fee Cloudbeds adds later (a fee attached to the online source, or an online booking whose source staff changed and whose rates or dates are then edited) is not detected: follow the rules in 4.B step 3 and remove such a fee with a negative Adjustment.
- Which email template `putReservation sendStatusChangeEmail=true` sends is unknown (Stage B test 12).
- Thai Stripe accounts accept Visa and Mastercard only (no Amex, JCB or UnionPay).
- In `stripe-mock` the search shows demo availability, which does not reflect mock holds.
- After a rollback to `BOOKING_ENGINE=cloudbeds`, Stripe's back link for an in-flight session lands on the Cloudbeds `/booking`, which does not call abandon: that hold is released by Stripe's 30-minute expiry (webhook) or the sweeper.
- With the default env, `/booking` and the homepage behave exactly as before, but their JavaScript is not byte-identical (a few KB of `next/dynamic` loader for the own engine), and the default deployment also has the routes `/booking/classic`, `/booking/return`, `/booking-preview`, `/booking-preview/return`, `/booking-preview/stripe-mock`, `/booking-preview/beam-demo`, `/api/stripe/webhook`, `/api/beam/webhook` and `/api/booking/{availability,checkout,status,demo-pay,sweep,abandon,mock-stripe,test-access}` (noindex, or 404/503/locked without their env vars). On the production deployment the preview is locked by default, and `/api/booking/availability` then answers 503 **without calling Cloudbeds**, so it never spends the read key shared with `/api/rates` and the droplet cron.

**Beam's limits** (design risks; the questions are `openQuestionsForBeam` in `beam-design-v2.json`):
- **No server-side GA4 purchase yet.** The `purchase` event is sent only from the return page in the guest's browser; a guest who closes the page before gtag.js loads is not counted. A GA4 Measurement Protocol send from the verified webhook is not built.
- **Status reads cost Beam calls.** Each check of a pending Beam booking reads the link and its charges (2 calls), so a return page left open makes about 126 Beam calls in its 15 minutes of checking; there is no cache (decided: a cache would go stale exactly when a payment lands). Beam's rate limits are unknown (question 6): if Beam allows fewer than about 60 calls a minute, a Beam-only throttle on status reads should go in before go-live. 429 answers are counted, never pause checkout, and 20 in an hour tell the owner.
- **A hold can block the unit longer than on Stripe.** An abandoned link's hold goes once the link expired (30 minutes; an ACTIVE link is disabled by us 2 minutes after its expiry) and a sweeper run reads it, so up to about 42 minutes with the 10-minute cron; a payment still PENDING keeps it `BEAM_PENDING_GRACE_MINUTES` (20) longer, and while Beam can't be read the hold stays until it can.
- **A very late payment is seen only for a while.** Released links are re-read for `BEAM_LATE_WATCH_DAYS` (7) days, longer (up to 30 days) only when their last reading showed a PENDING charge; the charge scan lists charges created in the last 72 hours (7 days on the deep pass). A charge that succeeds later than that is reported only by Beam's webhook (Beam documents very late `charge.succeeded`s). Whether a charge still PENDING when its link expired or was disabled can succeed at all is unverified (question 2): the rules assume it can.
- **Beam's unfiltered charge list is unverified** (question 8). If Beam refuses it, the sweeper alerts once a day and relies on the links it tracks (every link we create is tracked); a payment on a link whose record was lost is then found only through the webhook.
- **Per run the sweeper reads at most 500 open and 500 late-watch links** (`BEAM_TRACKED_LINKS_LIMIT`) and at most 50 pages of 100 charges per scan (`BEAM_SCAN_MAX_PAGES`; a scan that needs more fails the run).
- **The webhook has no event id, timestamp or IP list.** Nothing in the body is trusted: every event is re-read from Beam, and idempotency comes from our locks and markers. A resent or reordered event changes nothing.
- **Refunds are manual and partly by bank transfer.** Only cards can be refunded in part through Beam; PromptPay, Alipay and WeChat Pay only in full; LINE Pay, TrueMoney and ShopeePay not at all (section 8). This costs staff time and transfer fees. Refunds come from the available Beam balance.
- **The fee is a payment-method surcharge** (3% on cards and e-wallets, none on PromptPay). Beam's terms and the Thai card-scheme rules for it are unverified: a go/no-go item (section 10). At public prices plus 7% VAT on Beam's fee, overseas cards (about 3.48%) and AMEX (about 3.75%) cost us more than the 3% fee, and an Alipay user paying through the fee-free PromptPay QR may cost us the e-wallet rate (question 18).
- **E-wallets are all or none per link.** Beam enables "eWallets" as one group; single wallets can't be chosen per link, and whether the page then shows only the wallets approved on our account (WeChat Pay) is question 11.
- **Beam's maximum charge is a placeholder** (THB 999,999.99, question 6); a stay above it is refused before any hold ("message us on WhatsApp").
- **Beam sends no receipt.** The Cloudbeds confirmation email is the guest's written confirmation (owner decision 6); if it is ever switched off, beam-live stops taking new bookings and the paid return page becomes the confirmation.
- **The Playground webhook can't reach `localhost`**: Stage A confirms bookings through the return page.
- **The fallback needs a redeploy** (1-2 minutes; section 6, item 8). During a Beam outage the circuit breaker stops creating holds after 3 failed payment pages.
- **Preview and Production share one Redis** (shared real inventory): Stage B test holds count towards the 8-hold brake and the overlap check. A Beam mode without real Cloudbeds writes is refused on Vercel, so no preview can write fake holds there.
